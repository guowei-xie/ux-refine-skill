# 诊断透镜

九个透镜，每个透镜给出：看什么、典型症状、怎么取证（代码侧 / 截图侧）、依据的原则。
诊断时先看用户选定方向对应的透镜；其他透镜只记录严重问题，避免清单失焦。

## 0. 贯穿所有透镜的信号：提醒是设计的补丁

> 好的交互设计不需要靠提醒告诉用户该怎么做。

界面应该用自身的形态把用法「说」出来：
- **示能**：看起来就知道能点、能拖、能展开。
- **映射**：控件的位置和它影响的东西对得上。
- **约束**：错误的操作根本做不出来。
- **惯例**：沿用用户在别处学会的做法。
- **即时反馈**：操作的结果马上看得见。

知识放在界面里，而不是放在用户脑子里。所以当一个地方需要额外的文字提醒用户「怎么用、别做错、哪个才对」时，
多半是设计没把信息传达到位，提醒只是在打补丁。

**怎么用这个信号**：把提醒当成线索，反过来找它在弥补什么问题。
- 代码里搜：tooltip / popover / `title=` 里的操作说明、「注意」「请勿」「请先」「提示：」「说明：」开头的文案、
  新手引导（tour / guide / intro / onboarding / driver）、表单下方的长段说明、输入框 placeholder 里写的格式要求。
- 截图里看：说明文字比内容还多的区域、红字警告、「温馨提示」横幅。
- 用户素材里听：「要先跟新人讲一下」「我们有份操作手册」「培训时会特别强调」——每一条口头规矩都是一个设计缺口。

**常见的「补丁 → 根因」对应**

| 看到的提醒 | 背后的设计问题 | 更好的做法 |
|---|---|---|
| 「请使用新版订单管理」 | 新旧两个入口并存 | 收敛为一个入口（patterns A6） |
| 「状态 1 = 待审核」写在帮助文档里 | 界面显示内部编码 | 直接显示「待审核」 |
| placeholder「格式 yyyy-mm-dd」 | 用文本框收日期 | 用日期选择器，让错误格式输不进去 |
| 「请先选择门店再选择商品」 | 依赖关系没在界面上体现 | 门店未选时商品选择器禁用，并说明原因 |
| 「删除后不可恢复，请谨慎操作」常驻横幅 | 危险操作缺少分级防错 | 可撤销的给撤销，不可撤销的才弹窗确认并写明对象（patterns G1） |
| 「点击右上角 ⋯ 可导出」 | 高频功能被藏起来 | 把高频操作放到看得见的位置 |

**边界：不是所有文字都是补丁。** 三类信息本来就该有，不要误判：
1. **反馈**：告诉用户刚才发生了什么（「已保存」「导出中 40%」）。这是系统状态可见，不是教用户怎么做。
2. **高风险操作的防错**：不可逆、代价大的操作，写明后果的确认是必要的，哪怕设计已经很清楚。
3. **领域知识**：业务规则本身的复杂性（「退款超过 7 天需财务审批」），界面无法让它不言自明，这时说明就是内容本身。

判断方法：问一句「能不能通过改设计，让这条提醒变得不需要？」能，就是补丁，记为问题；不能，就是必要信息，
检查它是否写得清楚、出现得是时候即可。

## 1. 信息架构与导航

**看什么**：用户能否预测一个功能在哪里；菜单结构反映的是用户的任务，还是开发的模块划分。

**典型症状**（模块叠加型产品最常见）
- 一级菜单超过 7–9 项，或某个分组下塞了 15 个以上子项。
- 菜单按「开发批次」或「后端服务」命名，而不是按用户任务（如「数据中心2」「新版报表」）。
- 同一功能有多个入口但名字不同；或某个高频功能只能从某详情页的角落进入。
- 层级超过 3 层，面包屑缺失或与菜单不一致。
- 「其他」「工具」「更多」这类兜底分组越来越大。
- 新旧两版页面并存，用户不知道该用哪个。

**取证**
- 代码：找菜单配置 / 路由表，统计每级数量与最大深度；对比菜单文案与页面标题是否一致；
  搜「v2」「new」「old」「legacy」类命名的路由。
- 截图：展开菜单截图；从首页出发找某个高频功能，记录需要的点击次数。

**原则**：匹配用户心智模型（Nielsen #2）、Hick 定律（选项越多决策越慢）、渐进披露。

## 2. 视觉层次与布局

**看什么**：一眼看去，页面最重要的东西是否最显眼；页面区块是否分组清晰。

**典型症状**
- 页面上有多个同等强调的主按钮（三四个蓝色实心按钮并排）。
- 标题、正文、辅助信息字号字重区分不足，或反过来，层级太多。
- 区块之间间距随意，相关的东西没有靠近，不相关的没有分开。
- 关键数据（金额、状态）不突出，和普通字段混在一起。
- 页面过挤：筛选区占据半屏；或过空：宽屏下内容只占左侧一窄条。

**取证**
- 截图为主：眯眼测试（看缩小或模糊后的截图，最先注意到的是不是最重要的）；数每页主按钮数量。
- 代码：`style_inventory.py` 的字号、间距发散度；搜 `type="primary"` 等主按钮属性在单页内出现的次数。

**原则**：视觉层次、格式塔接近与相似原则、每屏一个主操作。

## 3. 一致性

**看什么**：同样的事情是否总以同样的方式呈现和操作。这是模块叠加最直接的受害者。

**典型症状**
- 样式值发散：十几种灰色、七八种字号、圆角 2/4/6/8 混用。
- 同类组件多份实现：多个各写各的表格封装、确认弹窗、上传组件。
- 同类页面结构不同：有的列表页筛选在上、有的在左；分页有的在右下、有的居中。
- 同一操作交互不同：删除有时弹窗确认、有时气泡确认、有时不确认；保存后有时跳转、有时停留。
- 绕开组件库手写的按钮、输入框，状态（hover / disabled / loading）不全。
- 日期、金额、空值显示格式不统一（`2024-01-01` 与 `2024/1/1`，`-` 与 `暂无` 与空白）。

**取证**
- 代码：`style_inventory.py`；搜相似组件名（`*Table*`、`*Modal*`、`*Confirm*`）；
  搜日期格式化调用方式；搜原生 `<button` / `<input` 与组件库组件的比例。
- 截图：同类页面并排对比。

**原则**：一致性与标准（Nielsen #4）、设计 token 化。

## 4. 任务流程效率

**看什么**：用户确认过的高频任务，完成需要多少步、多少次跳转、要记住多少信息。

**典型症状**
- 高频操作需要「进详情 → 点编辑 → 改 → 保存 → 返回列表」，而它本可以在列表行内完成。
- 不支持批量操作，用户要重复几十次同样的动作。
- 返回列表后筛选条件、分页、滚动位置丢失。
- 跨页面需要手动复制 ID、名称再粘贴到另一个页面。
- 每次都要重新选的条件没有默认值或记忆。
- 多步骤流程中途不能保存，离开就丢。

**取证**
- 截图走查：走一遍任务路径，记录步数、跳转、等待次数，形成一张「步骤表」。
- 代码：筛选状态是否进 URL 或缓存；有无批量选择（`rowSelection` 等）；列表到详情的跳转方式。

**原则**：效率与灵活性（Nielsen #7）、识别优于回忆（#6）、Fitts 定律（常用目标要大、要近）。

## 5. 反馈与系统状态

**看什么**：用户在任何时刻都知道系统在做什么、刚才的操作成功没有。

**典型症状**
- 请求过程中没有加载指示，按钮可重复点击，导致重复提交。
- 操作成功无提示，或提示一闪而过却很重要。
- 列表为空时一片空白，分不清是「没数据」「被筛没了」还是「加载失败」。
- 错误只显示「操作失败」「系统异常」，或直接显示后端原始报错 / 堆栈。
- 长耗时任务（导出、导入）没有进度，也不知道去哪看结果。

**取证**
- 代码：请求调用处是否有 loading 状态与按钮 disabled；列表组件是否处理 empty 与 error；
  错误提示文案来源（是否透传 `err.message`）。
- 截图：`ui_snapshot.py` 抓到的控制台报错；空数据页面截图；可用节流网络观察加载过程。

**原则**：系统状态可见（Nielsen #1）、帮助用户识别和恢复错误（#9）。

## 6. 表单与录入

**看什么**：填写是否顺畅、出错时能否立刻知道怎么改。

**典型症状**
- 字段很多却不分组，必填与选填不区分。
- 校验只在提交后统一报错，且报错不定位到字段。
- 能选的让人手输（日期、枚举），能自动带出的让人重填。
- 标签与输入框对齐方式在不同表单里不同；长表单无锚点导航。
- 编辑页与新建页不是同一个表单，字段顺序、校验规则不同。

**取证**
- 代码：表单 rules 定义位置与方式；新建和编辑是否复用；输入组件类型。
- 截图：表单整页截图；故意提交空表单看报错呈现。

**原则**：防错（Nielsen #5）、识别优于回忆（#6）、就近反馈。

## 7. 防错与恢复

**看什么**：危险操作有没有被挡住，做错了能不能撤回。

**典型症状**
- 删除、批量操作、状态变更没有确认，或确认文案只写「确定吗？」不说后果。
- 危险按钮与常用按钮紧挨、样式相同。
- 没有撤销，误操作只能找管理员恢复数据。
- 离开未保存的编辑页没有提醒。

**取证**：代码中搜删除、作废等关键动作的处理函数，看是否有确认与撤销；截图看危险按钮的位置与样式。

**原则**：防错（Nielsen #5）、用户控制与自由（#3）。

## 8. 文案与术语

**看什么**：界面说的是用户的话还是开发的话；同一个东西是否只有一个名字。

**典型症状**
- 同一概念多种叫法（「客户 / 用户 / 会员」「订单 / 工单」混用）。
- 界面露出内部字段名、枚举值、英文缩写（`status: 2`、`SKU_ID`）。
- 按钮写「确定」「提交」而不是具体动作（「创建订单」「发送通知」）。
- 提示语模糊、冗长或带责备语气。

**取证**：代码中收集界面文案（i18n 文件或硬编码字符串），按概念归类找同义词；截图看实际呈现。

**原则**：匹配真实世界（Nielsen #2）、动作导向的按钮文案。

## 9. 响应式与可访问性

**看什么**：在用户真实使用的屏幕尺寸下是否可用；基础可访问性是否达标。B 端系统通常不必适配手机，
先问用户实际设备分布再决定投入。

**典型症状**
- 1366 宽的笔记本上表格横向溢出、按钮被挤换行；超宽屏下内容拉伸变形。
- 文字与背景对比度不足（浅灰字配白底），小于 WCAG AA 的 4.5:1。
- 图标按钮没有文字或提示；仅靠颜色区分状态。
- 无法用键盘完成主要操作，焦点不可见。

**取证**：`ui_snapshot.py` 多视口截图；代码中搜仅图标按钮缺 `aria-label` / `title`；
对比度可用截图取色或样式值计算。

**原则**：WCAG 2.1 AA、包容性设计。

## 附：原则速查

Nielsen 十大可用性原则：
1 系统状态可见 · 2 匹配真实世界 · 3 用户控制与自由 · 4 一致性与标准 · 5 防错 ·
6 识别优于回忆 · 7 效率与灵活性 · 8 简洁美观 · 9 帮助识别与恢复错误 · 10 帮助与文档

常用定律：Hick（选项越多决策越慢）· Fitts（目标越大越近越好点）· Miller（短时记忆约 7±2）·
Jakob（用户期望你的产品像他们常用的其他产品）· 格式塔（接近、相似、连续、闭合）。

引用原则是为了让用户理解「为什么这是个问题」，不是为了堆术语。一条问题引一个最贴切的原则就够了。
