# 产物模板

## findings.md

```markdown
# 体验问题清单 · <项目名> · <日期>

范围：<模块 / 页面>　方向：<阶段 0 选定的方向>　取证：代码 / 截图 N 张 / 用户素材 / 对标

## 总体判断
<2–3 句：最主要的问题是什么、根因在哪>

## 问题（按优先级）

### F-01 <一句话问题>
- 透镜：<lenses.md 中的透镜名>
- 证据：<截图路径 / 文件:行号 / 用户原话 / 外链>
- 影响：<谁、在哪个任务里、后果>
- 依据：<一个最贴切的原则>
- 严重度：高/中/低　频率：高/中/低　改动成本：高/中/低　［速赢］
- 相关表现：<同根因的其他页面，可选>

## 已排除
- <用户确认是有意设计的项 + 原因>
```

## plan.md

结构效仿 plan 模式：先讲背景和目标，再讲做法，最后讲怎么验证。执行时在本文件勾选进度，它是唯一的计划真相源。

```markdown
# 体验优化执行计划 · <项目名>

状态：待批准 | 已批准（<日期>）| 执行中 | 已完成

## 背景与目标
- 为什么做：<阶段 0 的诉求 + 诊断的核心结论>
- 目标用户与高频任务：<…>
- 成功标准：<可观察的结果，如「订单列表 → 改状态 由 5 步降到 2 步」「全站主按钮样式统一为 1 种」>

## 已确认的方案决策
| 决策点 | 选择 | 理由 |
|---|---|---|
| 导航结构 | 侧边分组折叠（A2） | 用户多在单一业务域工作，改动最小 |

## 批次

### 批次 1：速赢（预计改动 N 个文件）
- [ ] 1.1 <改动> —— 对应 F-02、F-05
  - 文件：`src/...`
- [ ] 1.2 ...
- 验收：截图 <路由列表> 改前改后对比，检查 <具体看什么>；lint / 构建通过
- 风险与回滚：<…>

### 批次 2：基础设施（token / 公共组件）
...

### 批次 3：页面改造
...

### 批次 4：结构性调整
...

## 不做 / 延后
- <项> —— <原因：用户否决 / 需要后端配合 / 收益低>

## 用户需要配合的事
- <提供测试账号 / 确认文案 / 安排公告 …>
```

批次的划分原则：每批能独立构建、独立验收、独立回滚；公共组件先于使用它的页面；
改变用户习惯的结构性调整放最后，并附过渡方案。
